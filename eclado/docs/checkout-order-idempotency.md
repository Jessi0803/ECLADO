# 建單回應遺失與原單恢復

驗證日期：2026-11-24，Asia/Taipei。對應風險 R09。

原問題已在隔離 SQL 重現：訪客／會員各測原頁重試與重新整理，4 個案例都在第一筆建單提交、HTTP 回應遺失後建立第二張訂單。修正後以同一筆建單識別碼查回原單，再沿用既有付款流程；不會再次保留優惠券、贈品或雙錢包額度。

2026-11-24 已套用正式 migration、更新 schema cache 並發布前端；正式 SQL 回滾驗收與正式資產瀏覽器驗收已通過。詳見 [正式發布紀錄](checkout-r09-r23-production-2026-11-24.md)。

## 根因與修正

原有 `submittingRef` 只能阻擋同一頁當次連點。前端在收到 `order_id` 後才保存付款暫存；若 SQL 已提交但回應沒到，前端無法知道原單編號，重試會走一般建單。既有 flow／attempt 只提供診斷關聯，不是交易冪等保證。

新版於送出前保存一組隨機 UUID 與 256-bit 恢復憑證，依目前會員或訪客身分隔離在 sessionStorage。只保存識別碼、憑證與身分，不另存收件表單。無法確認儲存成功時不送建單，避免產生無法跨重整恢復的請求。

SQL migration 新增 `checkout_order_requests` 私有表及帶識別碼的兩個建單 overload。它們在同一交易內：

1. 驗證預期登入身分與 `auth.uid()` 一致。
2. 以識別碼取得交易級鎖，綁定身分、憑證雜湊與完整請求內容雜湊。
3. 已完成的同一請求直接回傳原結果；不同內容、身分或錯誤憑證不能覆寫原單。
4. 首次執行才呼叫既有權威建單函式，保存原結果後一同提交。原有報價、權限、優惠、庫存與錢包驗證仍由原函式執行；任何例外一同回滾。

新表不能由 anon、authenticated、service_role 直接讀寫，私有 creator 亦不開放 client execute。訪客必須持有恢復憑證；會員還必須是同一個登入身分。資料庫只存恢復憑證雜湊；建單結果含原付款授權，留在私有表，不放進遙測或公開查詢。

## 結果未知時的流程

- 原頁：保留表單並阻擋再次提交，提供「重新確認訂單狀態」。查回服務仍不可用時繼續阻擋，不能把查詢失敗當成沒有訂單。
- 重新整理：讀到未完成識別碼後自動查回原單；查回成功先恢復權威快照，再沿用原單付款。
- 查回確認沒有記錄：允許再次送出，但保留同一識別碼。即使先前請求只是晚到，兩次仍會互斥，不能各建一單。
- 舊請求仍在交易中：查回使用相同交易鎖，等提交／回滾後再判斷，不會在建單途中回報不存在。
- 原單已付款、取消或逾期：顯示原狀態，不新建金流；若已有金流，走既有查詢流程。
- 已保存原訂單的付款暫存後，才清除未完成建單憑證，交由原有付款恢復機制接手。

查回原單在重新報價前進行。這點對雙錢包與限量優惠很重要：第一單已保留額度時，重新報價可能已不再符合條件，但原單的既有快照仍有效。

## 部署與回復

1. 先在目標 staging 套用 [supabase-checkout-order-idempotency.sql](../supabase-checkout-order-idempotency.sql)，執行 [唯讀 verify](../supabase-checkout-order-idempotency-verify.sql)，所有欄位須為 true。以專用測試資料確認 PostgREST 能解析帶識別碼的 ordinary／wallet overload。
2. 正式資料庫依核准部署流程套用同一 migration，核對結果並更新 PostgREST schema cache；若未自動更新，可執行 `NOTIFY pgrst, 'reload schema';`。不重跑歷史付款／計價 migrations。
3. **確認 migration 與 schema cache 就緒後，才發布前端。** 新前端不會在 overload 缺失時降級成不具冪等保護的舊建單函式。
4. 發布後核對前端 revision，完成受控 staging／實機與原單恢復驗收。舊分頁未帶識別碼的建單不會自動得到此保護；不可由 flow 或同額購物車猜測並合併歷史訂單。

既有不帶識別碼的 overload 留給舊客戶端，相同購物內容使用新識別碼仍可建立另一筆合法訂單；這是「同一請求只執行一次」，不是限制重複購買。

發生問題時保留請求表與新函式，採仍理解未完成識別碼的相容修補。不要刪除請求或清空 result、不要只靠關閉前端畫面清除未知結果，也不能回退到會忽略未完成憑證並重新建單的版本。

## 適用邊界

本輪保障以保留同一請求憑證為前提。清除瀏覽器儲存、換全新瀏覽器，或歷史請求未帶識別碼，不能憑此自動查回；應依訂單查詢／客服證據處理，不能自動認定未建單。

目前沒有自動清理請求表。即使訂單已刪除，識別碼也不能因 TTL 消失而重新變成可建立新單；未來若縮減私有結果保留期，須保留不可重建的 tombstone，並另行驗證延遲重送與資料保留要求。
