# 自動活動商品分配：第二階段

日期：2026-10-21。第二階段的本機實作紀錄；後續 test 驗收見 [第三階段紀錄](automatic-price-allocation-stage3.md)。正式尚未安裝或發布。

## 本次行為

自動價格活動按商品件數分配，最大化合計折抵；不同商品可套不同活動，同件只能參與一個自動價格活動。百分比、固定金額、買 X 送 Y 與 legacy_discount 均納入。買贈占用買入及免費件，最低價比較池與同額判定依第一階段文件。

不建立活動組合、不新增活動編輯欄位，也不重整既有整套計價程式。滿額贈／滿件贈及優惠券的排序、門檻、疊加模式保持原計算；allow_all 改用各商品實際剩餘金額，而非把一個活動折抵攤至所有合格商品。

## 安裝及開關

- `supabase-automatic-price-allocation.sql` 是增量、單一交易、可重跑的安裝。須在現行會員／學生價格、代客訂單、活動適用對象與買贈 SQL 之後執行。安裝預設關閉，不自動啟用。
- `automatic_price_allocation_settings` 開啟 RLS，禁止 anon／authenticated 讀寫；一般前台或後台帳號均無切換權限。切換僅由資料庫部署角色執行。
- 關閉時保留舊單一活動分支；開啟時商城四參數報價、錢包報價及代客報價使用分配 helper。舊兩參數報價保留相容讀取；不支援確認報價的舊下單入口在開啟時要求更新頁面。
- 商城確認下單沿用現行檢查與交易，透過私有副本串接原本發票／購物金／贈品 creator。這些副本不授予客戶端執行權限；不使用可由客戶端設定的 session flag 來放行。
- 從目前安裝的權威價格函式建立私有商品價格解析副本，保留會員／學生價格及輸入驗證，將最低金額檢查延後至完整折抵後。原始函式若日後改動，開啟的新版會拒絕報價，避免繼續使用過期副本；後續價格 migration 必須同步更新副本與測試，或先關閉新版。安裝也會拒絕未知來源格式。
- `supabase-automatic-price-allocation-verify.sql` 是唯讀安裝檢查。

## 分配方法與界線

1. 合併同規格重複列，固定商品／規格數字 ID 排序；不改動訂單原始 items。單價來自權威解析，不採用前端分配。
2. 先依活動時間、身分與商品範圍篩選，再拆開不相連的活動／商品群組。
3. 單活動群組直接計算，買贈按數量批次挑免費與買入件，不逐件展開。
4. 重疊群組以可證明的樂觀上界剪枝搜尋每列分配件數，依合計折抵、活動折抵向量及固定歸屬順序取最佳結果。百分比按活動小計取整；固定金額每個活動只發一次。
5. 每個重疊群組最多128個「商品列×可參與活動」格，整筆分配共用20000搜尋節點預算。超限直接回報優惠計算範圍錯誤，不回傳未證明最佳的方案。大量重疊活動可能因此無法報價，這是第三階段上線前必須以真實活動配置驗收的界線，並非已保證適用所有配置。

金額使用 PostgreSQL numeric。小數固定折抵保持既有語意，百分比依合計取整。買贈小數取整沿用既有 helper 的作法，差額記在可付款件數；向下取整時可能形成商品列的微小取整補回，總金額仍一致且免費件不會再次當成可免費件。一般百分比分攤的最後一列吸收 numeric 除法餘差，避免加總偏差。

## 快照與畫面

- 不改歷史訂單。新快照使用獨立的 `automatic_allocation_version: 1` 與 `automatic_allocations`，避免覆蓋既有學生／贈品／錢包的版本欄位。
- 每筆 adjustment 記錄商品／規格、參與／免費／買入件數、資格與折抵範圍、小計、折抵、門檻、原始折扣參數及買贈取整差額；商城與代客均儲存。legacy 也寫入 `order_adjustments`。
- 多活動時不把合計金額綁至單一 promotion_id；舊欄位只在單一活動時回填。報價確認包含版本與分配，即使合計同額，優惠內容改變也要求重新確認。
- 購物車改取伺服器試算並列出多活動；請求失敗時明示估算與錯誤，結帳仍須重新驗證。結帳第一步也取得伺服器試算，代客確認沿用多筆列表；會員、訪客、代客付款、後台及列印補上多活動明細。舊快照無完整明細時保留合計顯示。
- 付款 API 僅增加回應中的優惠名稱、類型及金額白名單；不傳回內部分配、完整 pricing_snapshot 或付款憑證，不改銀行建單、金額核對或重試規則。正式顯示完整訪客／代客付款明細時需一併部署這個回應欄位調整；本階段未部署或操作付款主機。

## 本機驗證

- 第一階段27項契約測試，含169種單件金額組合。
- 隔離 PostgreSQL（PGlite）執行現行完整計價、建立訂單及錢包函式；105組生成案例與獨立逐件完整搜尋模型對照，另補買贈、三分之一比例上界及低價取整同額案例，另測重複買贈、固定與百分比取整、多活動快照、legacy 保存、同額變動回滾、舊入口拒絕、安裝關閉／重跑／來源不符原子回滾、身分／訪客限制、指定贈品、優惠券模式與買贈順序、開關不改歷史快照、雙錢包及客戶端權限。
- 壓力基準為合成資料：單一規格9999件買贈約1ms；20個重疊規格的案例117節點、約12ms；另以1節點預算確認超限明確拒絕。這是本機 PGlite 數字，並非 test／正式資料庫的效能承諾；商城既有每列99件上限仍保留，9999件僅直接測試私有核心。
- 桌面／手機購物車多活動與變更數量試算、既有購物車及會員訂單顯示測試；Vite 編譯與付款 API 測試。

第三階段已完成 test 安裝、實際角色登入、真實 RPC 交易回滾與資料庫效能驗收，詳見第三階段紀錄。正式備份／安裝／切換及付款 API 發布須另安排，不因第二階段完成而自動執行。
