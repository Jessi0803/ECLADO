## 必須先處理的正式環境問題

正式 `allocate_inventory_for_paid_order` 是舊的一般商品配貨實作，未辨識贈品庫存池；`release_inventory_for_order` 同樣只回補 `stock`，未依 `line_type='gift'` 回補 `gift_stock`。

因此不能直接新增四項贈品並扣贈品庫存：未來取消／退貨會回補到錯誤庫存池。現已準備 `compatibility-order.sql`，在兩支既有函式內加入僅命中此訂單的分支；不安裝全站新版 gift engine。修正前後的精確定義指紋見 `compatibility-manifest.json`。

- 退庫：只有此訂單明細位置 7–10（從 0 起算）的四筆本次補贈，且商品規格、活動、數量、配貨狀態、補贈標記及已消耗保留紀錄均吻合時，回補 `gift_stock`。保留原退庫事件流程，同步釋放四筆贈品保留，並將配貨標為已釋放。再次退庫不重複增加庫存。
- 配貨：此訂單一旦具有本次補贈標記／快照／活動／稽核紀錄，就拒絕再次呼叫整張訂單配貨。這會阻止取消／退貨後直接改回已付款或其他耗庫存狀態。若日後需要恢復，須另行人工審查或另建訂單，不自動重新保留贈品。
- 原有七筆配貨、此訂單補贈前的行為、其他訂單（即使帶有相同標記）的處理維持捕獲的舊版邏輯；不回寫其他訂單，也不擴充全站贈品政策。

`supplement-order.sql` 已改為只接受這份指定訂單相容實作的精確指紋。**正式仍是舊版，因此單獨執行補贈草稿依然會中止；不得略過檢查。**前次曾用全站贈品版本當隔離前置參考，本次已改為上述只影響此單的實作，沒有全站升級需求。

1. 執行前重新唯讀核對正式函式、訂單、活動及庫存；現有快照過期或有變更就停止並重新準備。
2. 審閱 `compatibility-plan.md`、指紋及隔離結果；取得後續正式執行授權後，才產生明確提交版本。
3. 應以 `review-bundle.sql` 的結構，在**同一交易**安裝相容分支並補贈。不要先分開提交函式，再另外處理訂單。此檔仍為預設 `ROLLBACK`，本次沒有送入正式 SQL Editor。
4. 函式安裝保留原 OID、owner、ACL、security definer 及 search_path；補贈失敗會連函式一起回滾。成功後仍須保留相容分支，供日後取消／退貨使用。
5. 若僅安裝相容分支、尚未補贈，可審查 `rollback-compatibility.sql` 還原原始函式。已有補贈紀錄後該回復腳本會拒絕執行，即使已取消也一樣，以免退庫／重新付款再出錯。後續要移除相容分支須另行審查，不可直接覆蓋。

此處保留所有回滾草稿，不提供可誤觸的一鍵正式寫入工具。庫存退回沿用既有取消／退貨時機，不代表執行金流退款或確認實體贈品已收回。
