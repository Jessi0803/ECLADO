# 指定訂單補贈的退庫相容計畫

僅處理 `ECL-20261103-155424-8308FA6E` 本次追加的四項贈品。沒有修改正式環境，沒有重查或宣稱更新原先的正式庫存快照。

## 選擇的方式

在正式既有兩支共用函式中新增**以訂單編號限定的分支**，保留其餘原始實作，不增加新 RPC、資料表或永久觸發器，不部署前端。

| 情況 | 本次方案行為 |
| --- | --- |
| 補贈前此訂單或其他訂單 | 沿用捕獲的原始配貨／退庫實作 |
| 本單已付款改備貨中 | 原有配貨不重扣；四項贈品也不重扣 |
| 本單補贈後取消／退貨 | 本次四項回補贈品庫存，配貨與保留紀錄轉為已釋放；原有七筆走原流程 |
| 再次呼叫退庫 | 已釋放配貨略過，不重複回補、不新增重複退庫事件 |
| 四項之一數量、規格、活動、標記或已消耗保留不符 | 拒絕本次退庫，交易回滾，交人工核對 |
| 補贈後再次整張配貨，包括取消／退貨後改回已付款 | 拒絕；需要另行人工審查或另建訂單 |
| 其他訂單即使帶同一補贈標記 | 不命中分支；維持原始行為 |

退庫條件同時核對：指定訂單編號、補贈位置 7–10、規格 38/87/104/105 與對應活動、`gift/promotion_gift` 配貨種類、每項已配貨／實扣／應贈均為 1、未曾釋放、原訂單明細補贈標記、以及同訂單／活動／規格已消耗保留紀錄。成功時只回補實際扣過的贈品庫存，保留原本退庫事件與狀態清理。

原矽膠刷位於位置 6，當初扣一般庫存，其配貨沿用原流程回補一般庫存；本方案不把歷史資料轉成贈品配貨，不另扣／返還這筆贈品庫存。原本其保留紀錄隨取消狀態轉為 released，屬既有狀態同步行為。

## 為何限制重新啟用

舊版完整配貨函式不辨識贈品庫存池。若取消後直接恢復付款，單純修正退庫仍會讓四項贈品再次扣到一般庫存。為保持單次補贈範圍，本方案擋下此單補贈後的整張配貨，而不增加重新預留、缺貨補贈或重算優惠等流程。

也會檢查已保存的補贈快照、活動及稽核紀錄，因此即使呼叫配貨時省略輸入的補贈標記，仍無法繞過。此限制僅在此單已有補贈證據時生效。

## 交易及安全邊界

- `compatibility-order.sql` 僅接受之前唯讀擷取的兩支函式精確指紋，未來有其他部署變更就拒絕覆蓋。安裝後再次核對預期指紋。
- 使用 `CREATE OR REPLACE FUNCTION` 保留原函式 OID、owner、ACL、security definer 及 search_path，並在交易內比對；不增加執行權限。
- 函式修正與補贈應以 `review-bundle.sql` 同一交易完成。已有補贈腳本的完整訂單／活動／觸發器指紋檢查照常執行。
- 修正與補贈失敗均整筆回滾，包含函式本身、庫存、保留、配貨與稽核紀錄。序號可能留下正常的跳號，不作為錯誤或重複判據。
- 安裝／補贈取得訂單表排他鎖，最長等待 5 秒，各陳述式上限 30 秒。成功提交後不保留排他鎖；日常退庫沿用既有規格及配貨鎖定順序。
- 所有 SQL 都以 `ROLLBACK` 結尾。`review-bundle.sql` 是本機審閱與驗證產物，本次未上傳正式 SQL Editor、未執行任何正式 DDL 或資料寫入。

## 執行前與回復

後續若要執行，先重新核對正式指紋、訂單內容、原配貨／保留、活動與四項贈品庫存。原資料或函式有變更就重新準備並驗證，不可刪除檢查或套用過期快照。取得正式執行授權後，才建立明確提交版本。

尚未補贈、僅安裝相容分支時，可用 `rollback-compatibility.sql` 的審查流程回復兩支捕獲的原始函式；它同樣預設回滾，拒絕覆蓋後來的函式改動。已有補贈後，甚至取消完畢後，都拒絕移除此相容處理；避免未來重啟訂單或其他操作重回錯誤庫存池。永久清理須另審訂單生命週期與資料狀態。

## 隔離驗證及限制

驗證使用 PGlite PostgreSQL，實際載入捕獲的原始庫存函式，執行生成的限定分支、原有訂單／庫存保護與補贈 SQL。另用原始函式作對照，確認原有七筆與其他訂單行為相同；結果記錄於 `compatibility-validation.json` 及 `validation.json`。

原有一般商品庫存採合成 fixture，只有四項本次補贈的庫存是先前正式唯讀快照。付款、返饋、通知及部分周邊觸發器採中性 fixture；保留紀錄狀態同步用 repository 實作，其正式內容未逐字擷取比對。未進行多連線競爭壓力測試或完整金流整合測試。

本方案處理的是既有取消／退貨流程中的庫存回補，不執行 Apple Pay 退款，也不新增實體贈品退回驗收流程。
