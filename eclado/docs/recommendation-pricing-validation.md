# 最後一步加購計價驗證

驗證日期：2026-11-03（Asia/Taipei）。

結果：`tests/recommendation-pricing-db.spec.ts` 共 20 項通過，耗時 56.1 秒。此輪只補測試與紀錄，沒有修改計價規則。

## 驗證方式

以 Playwright 操作實際結帳頁。身份及商品目錄由測試提供；報價、活動分配、錢包查詢及建單 RPC 則轉到隔離的 PGlite 資料庫，執行 repository 中的 SQL。返饋金由隔離的學生訂單完成後透過實際收益台帳產生，不直接修改帳戶餘額。

使用既有 `runRewardCheckoutDatabaseScenario` 建立基礎 schema 及錢包引擎，再安裝買 X 送 Y 與自動活動分配 SQL 並在隔離資料庫開啟功能。各情境以資料庫交易隔離，結束後 rollback；銀行 API 回應為模擬，所有未攔截之外部連線均中止。

測試先進入「確認付款」，才按推薦商品的「＋」。原購物內容為主商品 7,000 元，以及搭配品 3 件、每件 3,500 元；最後加購第 4 件搭配品後，商品小計為 21,000 元。

| 情境 | 活動折扣 | 購物金 | 返饋金 | 銀行應付額 |
|---|---:|---:|---:|---:|
| 最後一件達成買三送一 | 3,500 | 0 | 0 | 17,500 |
| 買贈＋另一商品折 500＋允許疊加的券折 200 | 4,200 | 0 | 0 | 16,800 |
| 上述疊加＋購物金 | 4,200 | 300 | 0 | 16,500 |
| 上述疊加＋返饋金 | 4,200 | 0 | 500 | 16,300 |
| 上述疊加＋雙錢包 | 4,200 | 300 | 500 | 16,000 |

所有情境運費為 0，每個情境都涵蓋桌機、手機，以及背景預覽已完成／延遲返回，合計 5 × 2 × 2 = 20 項。

## 核對內容

- 最新品項、規格及數量確實傳入最終報價和建單。
- 加購前已套用的優惠碼失效後，必須重新套用；重套後再確認訂單。
- 購物金與返饋金輸入在加購後保留正確金額。
- 活動折扣、總額、兩種錢包金額與銀行應付額，於最終報價、建單回應、資料庫訂單快照及付款請求一致。
- 資料庫 `order_adjustments` 實際保存買贈分配及合計折扣。
- 買贈使最後一件免費時，加購前後總額雖相同，仍保存加購後的四件數量及最新活動分配。
- 延遲的背景報價於建單後返回，不會覆蓋付款完成頁顯示的權威金額。
- 每次只建立一張訂單並發出一次付款請求，付款單建立後不再顯示加購。

## 重跑

須提供可用的隔離 PostgreSQL runtime；未提供時這個測試檔會 skip，不能視為驗證通過。

```sh
PGLITE_MODULE=/absolute/path/to/@electric-sql/pglite/dist/index.js \
  npx playwright test tests/recommendation-pricing-db.spec.ts \
  --project=chromium --project=mobile-chrome --workers=1
```

另已執行既有 `tests/integration/instructor-reward-checkout-db.test.cjs`，1 項通過，包含實際 SQL 的雙錢包共同最低付款 1 元、報價變更拒絕與錢包生命週期檢查。

範圍限制：驗證 repository SQL 在隔離資料庫的計算與前台串接，沒有對正式資料庫寫入、向正式銀行建單，亦不代表逐一重播正式環境全部活動設定。
