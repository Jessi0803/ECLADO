# 階段 5＋6 本機手動驗收

這份流程使用 `scripts/reward-acceptance-local.mjs`：實際前端、PostgreSQL 17.6、階段 2A～6 SQL／RPC／Ledger、銀行資料 AES-GCM 加密及原通知 dispatch 核心。Auth、PostgREST 傳輸、銀行收款／匯款、LINE／Resend 回應均為本機替身；不可當作正式銀行或訊息服務驗收。

## 啟動與隔離

在 `eclado` 執行：

```sh
EMBEDDED_POSTGRES_MODULE=/private/tmp/eclado-1b-postgres-tools/node_modules/embedded-postgres/dist/index.js node scripts/reward-acceptance-local.mjs
```

需 Node 24、本機專案依賴、上述 embedded-postgres 17.6 測試套件。只接受此測試 adapter，不接受正式 DB URL；Vite 不載入 `.env`，瀏覽器外部請求攔截至本機，未提供接點一律拒絕；通知 fetch 只接受兩個提供者固定 URL 並直接回傳假結果，不發出 HTTP。每次啟動建立一次性資料庫，停止後資料丟棄；Ctrl+C 停止後重跑即重置。產生的加密鍵只存於測試程序記憶體，不沿用正式金鑰。worker 以不含銀行金鑰的明確測試 env 呼叫；正式部署的程序隔離不在此驗證。

- 控制台：<http://127.0.0.1:5181/__acceptance>
- 老師：控制台「老師」→ `/account` →「師資返饋金」
- 管理員：控制台「管理員」→ `/admin` →「師資提領管理／返饋金通知紀錄／返饋金財務對帳」
- 唯讀管理員：控制台「唯讀管理員」。真實 SQL 權限限制，無 manage／notifications.send。

本工具是單一使用者、**依序切換角色**的驗收入口；不要同時以不同角色多分頁操作。它不測真實 Auth／PostgREST。5180 舊版純畫面 mock 不適用此帳務驗收。

初始老師 UUID `55555555-5555-4555-8555-555555555555`，學生 UUID `22222222-2222-4222-8222-222222222222`，管理員 UUID `11111111-1111-4111-8111-111111111111`，唯讀管理員 UUID `44444444-4444-4444-8444-444444444444`。全部是假會員。

初始 NT$1,000 由學生測試訂單＋管理員模擬確認收款＋delivered 入帳；不直接改餘額。造資料時只暫時開啟**隔離 DB**學生價，之後 OFF。商品、會員、購物金等一般頁面仍採畫面 fixtures，這不是全商城本機 Supabase。既有回歸 fixture 留有已知 `payment_unknown`；對帳應按來源 UUID／訂單辨識，不把整庫必須零 findings 當作驗收條件。

銀行休假測試表只排除週末，2026／2027 年額外假日為空；不是正式公會年曆。預計匯款日期依實際執行日期算，10 日 00:00 截止。2026-10-13 申請預計 2026-11-10。

## 1. 銀行資料、申請與通知

1. 老師頁填：銀行代碼 `807`、銀行名稱 `驗收銀行`、分行 `測試分行`、戶名 `驗收老師`、帳號 `12345678901234`，按「儲存收款銀行」。老師摘要應遮蔽戶名及帳號，僅保留末四碼。
2. 「申請全額提領」確認：申請 1000、費用 15、實匯 985、預計日期。不能輸入自訂申請額。
3. 成功後帳戶／可用餘額 0、提領保留 1000、狀態待匯款；老師不能取消。
4. 控制台「執行一次通知 worker」按兩次：首次展開管理員收件人，下次處理管理員 Email。收件匣看到老師 LINE 與管理員 Email，包含金額、手續費、實匯及日期，不含完整銀行、內部原因或交易序號。
5. 管理員「返饋金通知紀錄」核對已送出。再執行 worker 不應新增相同已成功事件的發送。
6. 申請後老師再次儲存不同銀行帳號，管理員「查看匯款銀行快照」仍應是申請時 `12345678901234`。畫面切換／失焦後完整銀行顯示清除。

## 2. 人工匯款完成

1. 管理員領取該申請「領取處理」→處理中。
2. **不要登入銀行、不實際匯款。**「記錄已匯款」輸入今日 YYYY-MM-DD、交易序號 `LOCAL-NO-BANK-001`、實匯 `985`。
3. 已匯款、已收費15、提領保留0、帳戶0，保留銀行快照與事件。
4. 再執行 worker，老師看到已匯款通知；再次 worker 不重發。只有「確認另寄新版本」才可稽核補發成功通知。
5. 對帳「執行財務對帳」：驗收老師不得有 account_ledger、account_projections、withdrawal_amount 等不一致。已知其他 fixture payment_unknown 維持人工列管，不是本次新增錯帳。

## 3. 明確失敗全額退回

從餘額0開始，控制台建立收入1000，再申請、管理員領取處理。

1. 「確認未付款並退回」，原因 `LOCAL 明確未匯款`，確認未付款。
2. 狀態明確失敗、帳戶1000、保留0、已收費0。原申請不能重匯；重新申請需新申請紀錄。
3. worker 發老師失敗／全額退回通知；多次 worker 不重複。
4. 對帳不得新增老師帳務不一致。

## 4. 結果不明與後續解決

將上述退回的1000重新申請、領取處理。

1. 「標記待查帳」，原因 `LOCAL 銀行結果不明`。
2. 帳戶0、保留1000，不能退回也不能再次申請該筆資金。
3. worker 通知「結果待查核」，不轉述內部原因；對帳出現此申請 withdrawal_unknown。
4. 在本機假定已查明未付款，再「確認未付款並退回」。應回1000，對帳後 unknown finding 解除／不再 present；歷史仍在。

## 5. 提領後退貨與負餘額

建議重啟得到乾淨1000，再建立收入200，帳戶1200。

1. 全額提領1200，費用15、實匯1185；帳戶0、保留1200。
2. 控制台「整筆退回最近建立的本機收入訂單」（200那筆）。帳戶-200、保留1200，原申請金額1200／實匯1185不變。
3. 老師不可再申請；按原申請處理完成1185（模擬）後帳戶仍-200。
4. 建立新收入200，抵銷為0；對帳不得把合法負餘額當作錯帳。再次退回同一收入訂單不應重複扣回。

## 6. 邊界與通知故障

每條金額案例從餘額0開始，或重啟後先完成初始1000提領。

| 案例 | 操作 | 預期 |
|---|---|---|
| 15元 | 建立收入15 | 不可申請 |
| 16元 | 先退回15收入再建立16 | 可申請16，費用15、實匯1 |
| LINE 5xx | 先設定5xx，再新申請／新通知，worker兩次以上 | LINE失敗後轉Email；帳務不變。依決策接受真實服務可能雙管道重複 |
| LINE timeout | 設timeout、worker | retry，同一防重鍵，不立即Email；提前本機重試時鐘後重跑 |
| timeout恢復 | 改success、提前時鐘、worker | 原通知成功，不重做提領／返還 |
| 重試上限 | timeout＋提前時鐘反覆6次 | unknown／人工查核，不再無限自動發送 |
| Email失敗 | 5xx先讓通知切Email，再改email-fail、worker | 永久錯誤保留失敗；帳務不回滾 |
| 更正 | 終態申請追加更正 | 只增加稽核；只有明確發送更正說明才建新通知 |
| 唯讀 | 切唯讀管理員 | 可看遮蔽紀錄；沒有銀行快照、處理、補發與執行對帳操作 |

收件匣代表**提供者呼叫嘗試**，timeout亦顯示，但不等於收件人已收到。替身不保證真實提供者重複防護，應以 Outbox／attempts／防重鍵另核對。

## 紀錄與停止條件

每條案例記：時間、角色、申請UUID、收入訂單ID、前後帳戶／保留、狀態、通知結果、對帳run／finding、通過／失敗／未執行。若金額不符或出現新 account_ledger finding，停止該案例，保留畫面及ID讓 Codex 查核；不手動修改 Ledger／餘額、不重匯款。

正式未驗證：真實登入與 PostgREST、正式 SQL 相依／部署、正式銀行年曆與收款憑證、LINE／Resend真實發送／逾時／防重、排程及金鑰隔離。此流程不授權正式 Migration、部署、commit／push，也不代表使用者已接受階段5／6人工驗收。
