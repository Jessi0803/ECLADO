# 自動價格活動商品件數分配與擇優規劃

日期：2026-10-21。狀態：第一、二階段本機實作與測試完成；尚未安裝至 test／正式或部署。第二階段細節見 `automatic-price-allocation-stage2.md`。

## 目標與範圍

保留目前單一活動的後台設定，不建立「自動活動組合」。將整筆訂單只選一個自動價格活動，改為不同商品可各自套用，同一件商品不能重複參與自動價格活動，並選取合計折抵最高的可行分配。

| 項目 | 處理方式 |
|---|---|
| 自動百分比折扣、固定金額折抵、買 X 送 Y | 納入新的商品件數分配與擇優 |
| 尚在生效的 legacy_discount 舊版複合價格活動 | 盤點並保留原始計算語意，納入候選，不能漏算或擅自拆成重複折抵 |
| 自動滿額贈、滿件贈 | 保持原有資格基準、贈品庫存與贈送規則 |
| 優惠券內活動 | 保持原排序、門檻基準、使用上限與核銷規則 |
| 優惠券與自動活動疊加 | 保持 coupon_only、allow_auto_gifts、allow_all |
| 會員／學生價格、購物金、返饋金、付款與庫存 | 維持原規則，驗證新優惠結果可正確銜接 |

擇優目標是「自動價格活動合計折抵金額最大」。不把優惠券、指定贈品價值、運費等一起做聯合最佳化。allow_all 取得新的自動價格優惠結果後，再依既有順序計算優惠券，因此最後金額可能改變，但優惠券規則不變。

## 商品分配規則

1. 從伺服器解析的會員／學生單價與實際商品規格件數開始，不信任前端價格或活動分配。
2. 一件商品最多分配給一個自動價格活動。同規格多件可拆分件數，不能把整列視為只能選一個活動。
3. 每個活動依「實際分配給它的商品」重算資格與折抵，不能再借用已分配給其他價格活動的商品湊金額或件數門檻。
4. 買 X 送 Y 的 X 件買入商品及 Y 件免費商品都算使用。once 最多一組，repeat 可多組；整組參與商品均須記錄，不能只記錄免費商品。
5. 買贈以「分配給自己的商品＋尚未分配且符合該買贈的商品」作為最低價比較池；已分配給其他有正折抵活動的商品退出該池。免費件須為該池最便宜的 Y 件／重複組數乘 Y 件，且都必須包含在自己的整組占用件數中。便宜餘數不能留在原價區而改送較貴品。repeat 組數為比較池件數除以 X＋Y 後無條件捨去，once 最多一組；只占用完整組數，剩餘件數不占用。範例：100、1000、1000、1000、1000 元且僅有買3送1，折100元；若100元商品確實參與另一個折10元活動，其餘四件可折1000元，合計1010元。零折抵活動不得占用商品來墊高其他活動優惠。
6. 固定金額活動每筆訂單仍只折抵一次；拆分商品不會多領固定折抵。百分比折扣按該活動分配商品的合計金額計算及取整，不逐件取整後相加。
7. 無優惠或未分配商品維持原價。折抵不得超過分配商品金額，金額需維持整數及總額一致。
8. 合計同額時，依 priority 小者、建立時間早者、ID 小者排序，逐項比較各活動折抵，較前活動折抵較多者優先；仍同額時比較固定商品／規格／件數順序的活動歸屬，未分配排最後。免費同價件亦依固定單位順序決定，不能因購物車列或資料庫回傳順序改變。此為新引擎的明確規則，包含 legacy；舊引擎 legacy 的單獨排序原本只使用建立時間與 ID，不回改舊訂單。
9. 自動活動占用件數與優惠券內部的免費件數標記分開保存。不能將新的自動活動排他規則誤套到原本允許疊加的優惠券；已免費單位與剩餘金額仍需遵守既有防止重複折抵、負數金額的檢查。

## 計價流程與最佳化方法

1. 解析商品、規格、會員資格與權威價格，篩選目前有效且符合適用對象的自動活動。
2. 依商品範圍重疊關係，將候選活動切成互不影響的小群。不重疊的群組分別計算後合併。
3. 重疊群組比較可行的商品件數分配；不能先挑單一優惠最大的活動、依活動排序搶件數，或只逐件比折扣，因為這些方式可能錯過更好的多活動組合。
4. 優先評估件數壓縮狀態、動態規劃／分支搜尋、快取與上界剪枝；實際方法須用固定折抵、門檻、買贈組合及 legacy 規則建立小規模完整搜尋基準後決定。避免在資料庫中無限制展開每一件商品或所有排列。
5. 合併各群最佳結果，產出每個活動的分配件數、免費件數、折抵及商品剩餘金額。
6. 依原優惠券疊加設定，保留或移除自動價格優惠，再執行原有優惠券流程及指定贈品流程。優惠券不需要自動價格活動時，避免執行無用的最佳化搜尋。
7. 依完整價格結果執行既有最低金額、運費、購物金／返饋金上限與訂單確認檢查。

正確性與效能都須先驗證。應測量既有購物車上限內的重疊活動數、規格數、件數及搜尋狀態；若不能在預算內證明最佳結果，不可靜默使用活動順序或貪婪結果並宣稱是最優惠。是否限制高複雜度活動配置或採明確的降級策略，需在實作設計與壓力測試後定案，不先承諾任意規模下都能即時找到全域最佳解。

## 程式與資料調整

- 新增必要的伺服器端自動優惠分配 helper，由現有商城及代客入口呼叫；不重整整套計價架構或合併既有重複函式。代客仍依顧客身分與手動／自動價格計算，不使用操作員身分。
- 將目前單一 automatic_id／automatic_discount 的選擇與剩餘金額分配，改為多筆 automatic_adjustments 與可核對的商品分配結果。
- 目前 calculate_buy_x_get_y 主要記錄免費件數；新核心需額外表達買入件數、整組使用件數與餘數，不能直接以 bogo_free_quantity 充當自動活動占用件數。
- 避免重建歷史完整計價引擎。採增量 SQL，保留當前權限、會員價格、付款與返饋金 wrappers，對未知函式版本中止安裝。
- 沿用 order_adjustments 保存多筆活動優惠，新增版本化分配快照。記錄活動 ID、商品／規格、參與件數、免費件數、金額、門檻、取整資訊與計價版本。
- 盤點所有讀取單一 promotion_id／promotion_name 的程式與 RPC。舊欄位維持相容語意，多活動明細以 adjustments／新快照為準，不把合計優惠錯標為某一個活動。
- 購物車、結帳、會員訂單、後台訂單、代客確認及列印顯示多筆活動優惠；後台活動編輯欄位原則上不增加。
- 舊訂單保持原快照；重新付款與訂單狀態更新不得用新引擎重算歷史優惠。過期報價在建立訂單時須重新驗證並要求再次確認。

## 驗收重點

| 案例 | 預期 |
|---|---|
| A 商品活動省100、B商品活動省200，兩者不重疊 | 合計省300 |
| 同一件商品有九折及八折 | 只使用較有利的可行分配 |
| 單一活動須占用兩件才能省250，另兩個相容活動各占一件省150 | 選兩個活動，合計省300，不能先搶250；若250活動無兩件門檻，可與另一個150活動分配不同件，則應省400 |
| 同規格多件，部分參與買贈、部分可參與折扣 | 依件數合法分配並比較，沒有重複使用 |
| 買3送1與另一活動重疊 | 買入及免費共4件都被占用，不可只排除免費件 |
| 8件但最低價僅1件、重複買贈 | 正確選最低與第二低價，且完整記錄參與件數 |
| 分配後不足滿額／滿件門檻 | 該活動不得成立 |
| 同固定折抵活動分配到多個商品列 | 只發放一次折抵 |
| 相同價格、餘數、零元商品及取整 | 結果穩定、無負值、總額一致 |
| 優惠券三種疊加模式、不同活動順序 | 保持原優惠券語意，正確使用新的剩餘商品金額 |
| 滿額贈／滿件贈、會員／學生價格、代客、錢包 | 既有規則與權限不退化 |
| 下單時活動或會員條件改變、報價版本過期 | 不接受過期優惠，要求重新確認 |
| 舊訂單付款重試、取消、退貨 | 原始金額與快照保持一致，無重複扣款或庫存異動 |
| 高度重疊、大量件數 | 有效能基準與明確界線，不以未證明最佳的結果冒充擇優 |

## 第一階段可執行基準

- 參考模型：`tests/helpers/automatic-promotion-oracle.cjs`，完整列舉每件商品分配給各合格自動價格活動或保留原價的可行解，再依上述目標與同額順序挑選。它只供測試，不能在正式計價路徑使用。
- 驗收案例：`tests/integration/automatic-promotion-allocation-contract.test.cjs`，包含27項測試、其中一項以169種單件金額組合對照直接可算出的答案。每個固定案例另驗證反轉輸入順序仍相同、件數無重複占用、免費件屬於參與件與折抵上限。
- 執行：於 `eclado` 目錄執行 `node --test tests/integration/automatic-promotion-allocation-contract.test.cjs`。
- 輸入為已通過資格／時間／會員篩選的活動及伺服器權威單價。模型不驗證登入權限、真實 RPC、庫存、優惠券計價、錢包或付款；疊加模式測試只確認是否進入自動價格分配。
- 測試參考模型限定非負整數新台幣及安全整數範圍，百分比以十進位有理數計算並半入取整。不得以此限制默默改變正式資料庫可接受的小數設定；第二階段須盤點金額欄位與既有小數資料，補 PostgreSQL numeric 對照案例。
- 最多列舉250000種歸屬；超過即明確拒絕。這只是測試工具界線，並非正式購物車限制或正式效能策略。第二階段以此比對最佳化 SQL 的結果，仍須實測壓力與逾時策略。
- 單位 ID 目前由測試直接指定為穩定字串。正式 helper 需以商品／規格／件數序號產生穩定鍵，先合併重複規格列，並驗證資料庫 ID 的排序規格；不可直接使用傳入列序號。

## 三階段實施與發布順序

1. 先固定活動分配、門檻、餘數與同額判定規則，建立小規模最佳解基準與反例測試。
2. 實作必要的分配 helper 與版本化快照，銜接現有商城／代客／優惠券流程及多活動明細顯示；同步完成效能基準，不進行額外架構重整。
3. 於 test 安裝增量 SQL，執行隔離測試、真實 RPC 回滾測試及登入後桌面／手機驗收。比較金額、快照、庫存、核銷與錢包帳務。通過後再安排正式備份、增量安裝、回滾驗收與程式發布；正式操作需另取得確認。

發布時新引擎採版本控制及受控切換，避免 SQL 與前端版本不一致時提前生效。回復時切回舊計價供新報價使用，保留新訂單及分配快照；不得刪除帳務紀錄或用全庫還原作為一般功能回滾。已發出的報價依版本與確認機制處理。

三階段已完成規劃、本機實作與 test 驗收；test 已安裝增量 SQL，驗收後新版開關維持關閉，暫存資料已清除。詳見 [第三階段驗收](automatic-price-allocation-stage3.md)。正式資料庫與發布狀態尚未變更。
