## 0. 執行原則與總進度

- **先驗證、後實作**：每階段先盤點實際檔案、RPC、資料表及部署狀態；有重大衝突先停下回報。
- **分階段獨立提交與驗收**：不得未經同意跨階段開發、執行正式 Migration 或部署。
- **部署方式（2026-10-12 使用者確認）**：後續一律透過 Git 整合自動部署；不得直接操作 Vercel CLI／後台部署、promote、alias 切換或 rollback。正式發布及回復均透過 Git 版本變更與既有自動部署流程處理；不擅自修改 Vercel 設定或合併 main。commit／push 前須核對目標分支會觸發的部署環境與使用者授權範圍；7A已唯讀確認 main 對應 Production、師資分潤分支對應 Preview；Preview仍寫死正式Supabase／付款URL，不能視為隔離測試環境。不將 Git push 一律視為僅供備份。
- **最小侵入**：保留既有會員定價、活動、優惠券、贈品、購物金、代客開單、庫存與永豐付款流程。
- **後端為權威**：價格、師生權限、返饋金、錢包扣抵與提領不得僅由前端判斷。
- **功能開關**：師生設定可以先建，但正式學生價須等訂單快照與返饋 Ledger 均驗證完成後才能啟用；一般與代客訂單都必須受後端開關約束。
- **財務資料可追溯**：金額計算、返饋入帳／扣回、錢包保留／扣用／返還、提領均需冪等、可對帳並具備授權保護。
- **測試隔離**：不可在正式環境建立測試訂單、付款或任意修改資料。

## 1. 已確認的業務規則（後續階段不得自行更改）

### 1.1 師生關係與學生價

- 學生保留現有 `pro` 角色；不新增 `student` 角色。老師角色為 `instructor`。
- 一位老師可有多名學生；學生同時間最多一位有效老師。
- **只有具備相應權限的管理員**可建立、更換、解除師生綁定，設定／修改老師學生類型及修改兩種全域折數；老師與學生均無修改權。
- 學生類型設在**老師**身上，所有其名下學生共用：`student_1` 預設 `0.90`、`student_2` 預設 `0.95`；老師初始不設定類型，設定後才能綁定學生。V1 無商品個別學生折數。
- 學生價＝**既有美容師專業價** × 對應全域折數；沿用既有商品／規格定價與整數四捨五入。未綁定的 `pro` 維持原價。
- 保留 `pro` 原有最低訂購額、運費、優惠券與訂購限制；須依現有實際計算順序整合，不擅改既有規則。
- 老師不再是 `instructor` 或學生不再是 `pro` 時，**保留關係但暫停學生價**；雙方恢復符合資格時，原有效綁定可恢復套價。歷史訂單與返饋不因角色變更重算或刪除。
- **2026-10-12 使用者補充確認**：老師已有有效學生時，清空學生類型仍保留綁定、暫停價格資格，重新設定後恢復；Auth 帳號刪除時自動結束涉及該會員的有效綁定，保留 UUID 與異動歷史、不複製聯絡個資。1B 以 profiles 刪除連動實作，不修改既有刪除 API；未來有返饋帳務時的刪除策略仍須在 2A／2B 另行設計。
- **2026-10-12 階段3確認**：目前 instructor 才可本人查詢返饋，降級停止查詢、保留帳務與歷史，恢復後可查；顯示商品金額與返饋可推算比較價，使用者接受此推算，只禁止直接回傳比較價／折數欄位。
- 老師可見自己學生姓名、屬於自己的訂單商品及返饋資訊；**不可見學生電話、Email、地址**。學生只能看自己的老師與學生類型，不能看到師資比較價／返饋。管理員依後台權限操作。

### 1.2 返饋計算與訂單快照

- 一般學生訂單逐項返饋＝`max(0, 學生類型價（其他活動優惠前）－實際師資商品單價) × 數量`。
- 管理員代客學生訂單**也產生返饋**：AUTO 用後端學生類型價；MANUAL 用管理員指定的商品單價；逐項套同一公式，管理員**不能直接編輯返饋額**。AUTO／MANUAL 必須明確標記，不得從金額相等與否推測。
- 自動活動、優惠券、購物金與返饋金折抵**都不降低返饋計算基準**；每項返饋最低為 0。老師自己的訂單不產生學生返饋。
- 師資比較價依「商品個別師資設定 → 後台全域師資設定 → 預設 `0.70`」回退，**須核對真實價格函式**，不可寫死七折；如原有售價路徑需要修正，先獨立回報。
- 建單時凍結老師、學生、價格類型、比較價、數量、逐項返饋與總額；歷史換綁／調價不追溯。學生不能讀到受保護的比較價快照。
- 歷史人工補登訂單、訪客訂單事後歸戶均**不追補**；老師自身訂單不計。

### 1.3 返饋入帳／扣回

- 建單建立待入帳紀錄；**有效付款且**訂單到貨 `delivered` 或取貨 `picked_up` 後才正式入帳一次。
- 未入帳前取消則作廢待入帳；已入帳後整筆取消／退貨則全額扣回一次。V1 不做部分退款返饋拆算。
- 扣回後**允許負餘額**，未來入帳先抵銷；晚到付款回呼、重複狀態更新不得重複入帳或使已取消訂單錯誤復活。
- 返饋 Ledger 與現有**不得負數的購物金**分開，採可追溯且具交易保護的帳務設計。

### 1.4 返饋金購物折抵

- 老師**一般網站自行結帳**可與既有購物金並用；返饋金僅折抵商品、不得折抵運費，兩錢包總折抵不可超過活動／優惠券後可折抵商品額。
- V1 **銀行實付總額至少 NT$1**，不做零元結清；限制是銀行應付總額，不是要求每個錢包各留一元。
- **代客訂單 V1 不得使用返饋金折抵**（但可產生學生返饋）；原代客購物金流程不變。
- 原付款核對公式 `payment_amount + shopping_credit_amount = total`，雙錢包階段才依後端實際欄位／契約安全擴充。
- 階段4已於本機擴充為 `payment_amount + shopping_credit_amount + reward_credit_amount = total`；正式尚未套用，不將本機契約誤當正式現況。
- 2026-10-12使用者確認：明確付款失敗只釋放返饋金，購物金仍沿用取消／逾時釋放；原訂單重試重新驗證目前instructor與可用額並保留原額。
- 既有返饋hold遇角色降級或學生退貨造成負可用額仍履行；禁止新增／重新保留，不重新取消已承諾hold。
- 釋放後未重新保留而晚到有效收款：保存證據／帳務異常，阻止自動扣用及啟用訂單，由管理員處理；不自動扣成負數／銀行退款。
- 取消訂單不得復活保護範圍：使用返饋金或已有學生返饋快照；其他既有取消後晚付款改paid與代客重新配庫存路徑經確認獨立列管，保留原行為。

## 3. 各階段工作包與驗收條件

### S1｜付款重試授權風險（優先、獨立）

**目的**：釐清既有付款重試是否存在越權、錯誤重複付款或不一致風險，不把新功能與金流安全修補混在一起。

- 先取得確切路由／RPC、呼叫權限、可重現條件、影響範圍與安全測試方式。
- 若確認漏洞，提出**最小修補**及既有正常重試流程回歸測試；不得在正式環境做破壞性重現。
- 是否立即修補與部署須另行批准；未修補前記錄風險、補救方式與是否阻擋後續上線。

**驗收**：附前後授權證據、回歸測試、修改檔案與部署決策。**未完成／未經核准不得自行改正式金流。**

### 1B｜師生綁定、學生類型、後台設定

**範圍**：只新增資料及管理能力，**不改商品售價、結帳、付款、購物金或返饋 Ledger**。

- 設計學生類型全域折數、老師類型、單一有效師生綁定及異動稽核（表名依現有 Schema 決定）。
- 管理員設定折數／老師類型、建立／換綁／解除；老師與學生只能按授權查詢。
- 老師初始無類型，不可綁學生；首次綁定資格驗證；後續角色變更保留綁定但停止套價。
- 防止競態造成學生同時綁兩位老師；異動須可追溯操作者與時間。
- 考慮 `profiles` 刪除後關係歷史留存與參照完整性；不可讓財務歷史被連鎖刪除，個資保存範圍需最小化。
- 後端 RPC／RLS／EXECUTE 權限落實管理員獨占寫入；提供未來價格與快照讀取所需的安全上下文。

**驗收**：只有管理員能異動；學生唯一綁定；類型與角色暫停／恢復符合預期；原會員售價及建單完全不變；Migration 可回復。

### 1C｜學生價格與代客 AUTO／MANUAL 整合

**範圍**：商品列表／詳情、規格、購物車、結帳、後端 quote／create、代客自動與人工價格、活動／優惠券／運費／最低訂購額、價格刷新。

- 後端權威套用「專業價 × 學生折數」，沿用現有 rounding 與價格／優惠計算順序；不影響其他會員角色。
- 代客每個商品明確區分 AUTO／MANUAL；AUTO 後端重算，MANUAL 後端依管理員權限驗證指定單價；不由價格是否相同推測模式。
- 釐清舊瀏覽器／舊 API 請求相容性，價格不一致時要求重新確認，避免靜默改價。
- 新返饋比較價遵守既定師資回退規則；若現有原售價路徑需修正，**另報告、不順便修改**。
- 設計**後端強制**功能開關，關閉時一般／代客新建單維持原行為，管理員仍可先管理師生資料。

**驗收**：各角色與各規格價格回歸、代客 AUTO／MANUAL、折扣與運費正確；正式學生價**保持關閉**直到 2A＋2B 通過。

### 2A｜一般／代客訂單返饋金快照

- 建立共用的逐項返饋計算核心：一般學生價、代客 AUTO 學生價、代客 MANUAL 指定價，減去**實際師資比較單價**，每項 `max(0, 差額) × qty`。
- 返饋比較基準在活動／優惠券／錢包折抵之前；師資比較價按商品個別→全域→預設回退；確認規格、rounding、贈品／非商品項目是否應排除（**若既有需求未明，先回報決策**）。
- 建單交易內保存老師歸屬、學生識別、類型、價格／數量、返饋及來源模式快照；敏感欄位放受保護資料表。
- 排除老師自身、歷史人工補登、訪客後續歸戶等非適用訂單。
- 支援會員刪除後仍可對帳與追溯，且不無限制保留個資。

**驗收**：一般／代客同公式、人工價正確、促銷不影響返饋、快照不可重算、學生不可讀比較價、併發建單不漏記。

### 2B｜返饋帳戶、Ledger 與訂單生命週期

- 與購物金分開建立帳戶及不可任意改寫的 Ledger；建單待入帳、有效付款且 `delivered`／`picked_up` 後入帳一次。
- 取消待入帳、已入帳後整筆退貨／取消扣回一次；允許負餘額及未來返饋抵銷。
- 檢查所有訂單狀態修改入口（後台、付款回呼、取消、退款）；晚到回呼不能復活取消單或重複發放。
- 交易鎖、唯一鍵／冪等鍵、錯誤重試及對帳設計。

**驗收**：重複事件、並行更新、取消後付款、已入帳後退款、負餘額與重入帳防護均通過。

### 3｜老師／管理員返饋金查詢

- 老師看自己學生**姓名**、自己歸屬的歷史學生訂單商品／數量／金額、待入帳／已入帳／扣回與可用餘額。
- 管理員按權限查師資、學生關係與返饋帳務；提供異常查核。
- 以**限定欄位 RPC／後端查詢**輸出，不直接開放老師讀學生完整 `orders` 或會員資料。
- 歷史訂單查詢授權依**訂單成立時老師快照**，不是目前師生關係。

**驗收**：老師無法讀其他老師資料、學生聯絡資訊、師資敏感比較價；管理員權限分級有效。

### 4｜返饋金折抵與雙錢包

- 一般師資自行結帳可使用返饋金及購物金，保留、付款成功扣用、失敗／取消釋放、整筆退貨返還。
- 合計折抵不得超過促銷後**可折抵商品額**；返饋金不能折運費；**銀行實付總額 ≥ NT$1**，不做零元結清。
- 依實際付款欄位擴充金額一致性公式（目前只有 `payment_amount + shopping_credit_amount = total`）；前端、後端、永豐付款／回呼必須一致。
- V1 代客訂單**不能使用返饋金折抵**；既有代客購物金、庫存、付款分享流程不受影響。
- 鎖定與並行測試避免重複保留、超額扣用或兩錢包互相競爭。

**驗收**：舊購物金單獨使用不變；雙錢包＋運費＋最低 NT$1 正確；支付失敗／回呼重試與退貨帳務一致。

### 5｜銀行資料、全額提領、人工匯款

- 老師自行設定銀行資料；申請時快照。可用額**嚴格 > NT$15** 才可申請，必須全額，手續費 15，實匯為申請額減 15。
- 申請時原子保留／扣除全額；不需核准、不允許老師取消；管理員記錄人工匯款完成或失敗。
- 提領申請後若發生返饋扣回，不改原申請額；帳戶可變負數。
- 提領與匯款防重複，敏感銀行資料加強存取權限與紀錄。

**本階段開始前必須決策**：每月 10 日截止時間／時區、假日順延依據、失敗匯款的餘額／手續費處理、老師降級後提領資格、必要的匯款憑證與狀態流轉。

**驗收**：門檻邊界（15／16）、同時申請、負餘額、退款後申請不變、匯款狀態與金額對帳。

### 6｜LINE／Email 通知與對帳

- 老師申請提領通知：LINE 優先、Email 備援；管理員收到申請 Email；匯款完成後通知老師。
- 使用非同步 outbox／佇列、冪等事件、失敗重試及可查詢發送結果；通知失敗**不得回滾財務交易**。
- 對帳：訂單快照↔返饋 Ledger↔帳戶餘額↔提領保留↔匯款紀錄；提供異常清單及人工排查流程。

**驗收**：重複通知與重試可控、失敗可補發、帳務差異可追蹤。

### 7｜整合回歸、部署與正式啟用

- 完整回歸：`consumer`／`pending`／`pro`／`instructor`／`distributor`／`staff`、規格、價格回退、最低訂購額、免運、活動、優惠券、贈品、代客、購物金、永豐、庫存、退款、RLS、刪除會員、舊瀏覽器。
- 財務情境：一般與代客返饋、換綁、角色降級／恢復、重複事件、晚到回呼、負餘額、雙錢包、提領及通知。
- Migration 依賴／部署順序、備份與回復計畫、觀測告警、功能開關與灰度啟用、人工驗收。
- **正式啟用學生價前**：至少 1B、1C、2A、2B 的後端一致性與財務安全驗收通過，S1 風險已處理或有明確核准的風險處置；不得因前端完成就啟用。

**驗收**：測試報告、正式環境變更清單、回滾演練與上線核准均具紀錄。

權威公式：

```text
商品上限 = max(0, min(floor(subtotal - discount), floor(total - 1)))
shopping_credit_amount + reward_credit_amount <= 商品上限
payment_amount = total - shopping_credit_amount - reward_credit_amount
payment_amount + shopping_credit_amount + reward_credit_amount = total
```

此 subtotal／discount／total 來自既有後端商品、活動、優惠券及運費核心。不是每錢包各扣一元。原只使用購物金與不使用錢包路径保留；新路徑也測試兩者。

新增 RPC：

- `get_my_reward_credit()`：authenticated，目前 instructor、auth.uid 自己；signed／available／reserved／version。
- `quote_order_with_wallets(jsonb,text,text,text,bigint,bigint)`：anon／authenticated 可呼叫；未登入／非 instructor 的非零返饋折抵拒絕；原 quote 核心＋雙錢包上限／帳戶驗證。

#### 帳務、鎖與冪等

| 消費事件 | 可用 balance delta | reserved delta | 後續狀態 |
|---|---:|---:|---|
| spend_reserve | −amount | +amount | reserved |
| spend_consume | 0 | −amount | consumed |
| spend_release | +amount | −amount | released |
| spend_refund | +amount | 0 | refunded |

`balance` 保持 signed 可用帳務額；`pending_balance` 為待入帳收入，`reserved_balance` 為消費保留，互不混合。只有收入 reverse 可造成負數；消費不允許新透支。退回消費可能抵銷既有負額。

Ledger unique(order_id,event_type,reservation_cycle)；同 cycle 不重複，retry 新 cycle。來源原因包含建單、重試、有效付款、明確失敗、取消／逾時／退貨。收款證據獨立不可變，paid_at／人工 paid 不足以扣用。

生命週期先鎖 order→reservation→Auth 父列→account；新建單先取得本人 Auth／profile，再固定購物金 account→返饋 account，沿用既有購物金同步的順序，避免雙錢包鎖倒置。同帳戶序列化、版本檢查、unique event 及整筆交易回滾，不以直接修改歷史餘額補洞。

角色降級不取消既有 hold；重新保留必須重新驗證。明確失敗釋放／逾時取消釋放／未付取消釋放；已 consume 取消或整退 refund。付款成功／取消競爭，終止訂單不復活，晚收款留下 exception。已正常退款後的重複原成功回呼不建立虛假新異常。

老師餘額非零、待入帳非零或 reserved 非零禁止刪除；沿用零餘額無義務可刪／保留 UUID 歷史策略。既有代客 Auth 刪除衝突仍獨立列管。

現有balance已扣購物保留，因此全額可提領=max(0,balance)，不再次扣reserved_balance。新增withdrawal_reserved_balance與Ledger withdrawal_reserved_delta／after，分開顯示購物與提領hold，但同一帳戶row lock及版本。

| withdraw_complete | 0 | −申請額 | 原申請額；實匯=申請額−15 |

## 對帳不變條件與人工查核

私有STABLE `reward_financial_checks()`同statement MVCC唯讀核對；`run_reward_reconciliation`用advisory transaction lock拒絕並跑，相同request-key回原結果。先有界計數，V1來源50,000／異常10,000筆上限；超限或失敗記failed，不解除舊異常。

- 帳戶四餘額＝Ledger四delta加總、各after＝同帳戶id running sum；FULL JOIN抓缺帳戶。balance已扣保留，不重扣，負balance合法。
- snapshot老師／總返饋／逐項reward＝state／收入Ledger；pending一次、credit／cancel互斥、reverse只在credit後一次，獨立標重複credit／reverse。有效receipt與完成／終止一致，不靠paid_at，不查現價重算。
- pending帳戶＝pending income；購物hold＝reserved reservations；提領hold＝pending／processing／unknown原額。
- 每購物cycle reserve一次、consume／release互斥、refund在consume後一次，reservation／訂單／receipt／退款與三項付款公式一致；缺reservation／孤立spend列異常，付款失敗後訂單仍unpaid而released合法。
- 提領reserve一次、complete／release互斥；paid需net=amount−15、fee_charged15及憑證；failed全額release、fee_charged0。quoted fee15與failed charged fee0不誤報。unknown保留不改結果。
- 原晚付款exception／unknown匯款列人工查核；合法已取消pending order刪除不一律誤報。實匯憑證仍是管理員輸入，不代表銀行資金已驗證。

finding唯一rule／source，first／last_seen、expected／actual、present及run ID；重掃復用、不DELETE。完整成功掃完才解除未再見到的異常；失敗rollback finding更新，保存failed run＋SQLSTATE，不保存敏感原始error。原immutable payment exception未新增結清制度，保留供人工核對。

只發現／記錄／查詢；沒有餘額修正、Ledger重寫、重發返饋、退款、銀行匯款或unknown改paid／failed操作。通知列表20筆、近期attempt上限200、對帳finding20及run10；完整attempt歷史仍存在DB，不宣稱目前UI提供無限歷程匯出。
